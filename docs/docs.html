欢迎使用

这份文档是 Solen Design 的使用说明。所有文档都在这一页里切换，下面是每一篇的去处。

组件怎么用

打开UI 组件画廊，按分类逛：每个组件都能在线预览、实时调参数，看中了就进组件页复制完整代码包。多数组件提供 React、Vue、Svelte、Solid、Preact 与原生 DOM 六种入口，共享同一套框架无关的引擎——行为和 props 完全一致，换框架不用重学；少数纯 CSS/JS 组件以 React + CSS 形式交付。

组件页还带一张 API 表：每个选项的名字、类型、默认值和作用，复制代码前扫一眼就知道能调什么。每个组件都有一份复刻提示词，点「复制提示词」就能交给 AI 从零复刻出和展示页一致的效果。

换成你的样子

颜色、字阶、间距、圆角、阴影全部是收敛的 --sd-* 令牌，组件不写死任何数值。明暗是一套系统：语义令牌用 light-dark() 跟随 color-scheme，默认跟着系统设置走，也可以钉在任何子树上局部翻转。改品牌色只需要覆盖一个变量：

:root { --sd-accent: light-dark(#0f62fe, #4589ff); }

令牌分三份文件各管一层：src/tokens/palette.css 是原始色阶，semantic.css 是要用的语义令牌，scales.css 管字阶、间距、圆角与阴影。工作台固定浅色；语义令牌仍用 light-dark() 跟随 color-scheme，接入方可以按需实现双主题。

我是谁

一个美术出身的接单侠，一个低精力但爱琢磨的人，一份摊开了的自我介绍。

2026 年 11 月 16 日

署名：Solen·云

事情是这样的。

每次要在什么场合介绍自己，我都会卡壳。

不是没有名字。名字好说，大家可以叫我云。卡壳的是职业那一栏。你说我是设计师吧，我现在一大半的活儿是 agent 定制和软件开发。你说我是程序员吧，我偏偏是从画笔里泡出来的。你说我是搞 AI 的吧，这话我更不敢接。

填表格的时候，职业那栏我打过设计师，也打过开发者，后来干脆打自由职业。每个都对，每个又都不全。

而且我发现这不是我一个人的毛病。身边做独立职业的朋友，个个都介绍不清自己在干嘛，因为大家干的都不止一件事。这个时代给个人开了太多扇门，门一多，名片就写不下了。

所以想了想，干脆写一篇文章，把我自己摊开讲清楚。以后再有人问，我就把这篇甩过去。

云这个名字好不好听另说，反正挺配我的性子，飘得慢，不扎眼，但待得久。这篇你就当一朵云的自我介绍，慢慢看。

从根上说起

先从根上说起。

我是美术出身。高中开始学美术，一路画到大学毕业，素描、色彩、速写，那套童子功一样没落下。按原来的剧本，毕业应该进设计公司或者画室，往设计师的方向一路走下去。事实上我也确实是这么开始的，大学的时候就开始接设计单。

那时候接单是纯手搓，哈哈哈。

真的就是纯手搓。一张图一张图地抠，一个页面一个页面地画，所有的东西都从自己的手和时间里过。那段日子苦是苦，但有个好处，我的审美和手上功夫，就是在那几年里被一张一张图喂出来的。现在回头看，那段时间交的学费，一分都没白交。

手搓的时代没有捷径，改稿就是重画。那几年把我的眼睛练得很毒，看一个界面歪了半个像素都难受。这双眼睛后来成了我吃这行饭的底气，AI 能替我画图、替我写代码，但替不了我看出「哪里不对」。

手搓还有一个副作用，是你对成本特别有体感。你知道一张图要烧掉自己多少个小时，所以每一单都算得清清楚楚。后来用上 AI，成本下来了，但这段经历留了个宝贝在我身上，我知道什么东西贵，也就知道什么东西值得让 AI 去变便宜。

学美术的人都知道，前期的进步是看不见的。你画一百张烂画，感觉不到自己变强，直到某一天突然开窍。我后来琢磨 AI 也是一模一样的曲线，前期全是挫败，突然某天就通了。所以现在我对「学不会」这件事不太慌，我知道曲线长什么样。

碰到 AI

然后我碰到了 AI。

也是大学的时候接触的。不过那时候的 AI，说实话还没这么牛逼，跟现在完全不是一个物种。一开始我也没觉得它能改变我什么，顶多算个好玩的玩具。

转折出现在一个特别功利的念头上。单接多了我就开始琢磨，AI 这东西，对我接单到底有什么帮助。

就是这个念头，把我带进了另一个世界。

我开始拿 AI 试各种活儿。能用的地方直接用起来，不好用的地方研究为什么不好用。自己一点点琢磨，也跟着一些大佬学习，看他们怎么用，怎么想。

我的琢磨方式很笨，就是一个一个试。让它干一个具体的活儿，成了就记下来为什么成，砸了就记下来为什么砸。笔记攒多了，慢慢就摸到它的脾气。大佬们的分享给了我很多现成的答案，但真正长在我身上的，是自己摔的那些跟头。

跟大佬学习这件事我还有个心得，看他们的成果用处不大，看他们的过程才值钱。成果是别人的，过程里的取舍才是能搬回家的。自己踩过坑，再对照大佬的做法，两边一对，进步最快。

慢慢地，我能接的活儿从设计单，扩展到了 agent 定制、软件开发，这些以前想都不敢想的领域。

一个美术生，开始写代码接开发单了。

听起来像叛逃。但我后来想通了，这不是叛逃，这可能是回家。

你想想达·芬奇。画家，同时也是工程师，手稿里画满了飞行器和水利设施。在文艺复兴那会儿，画画的和造东西的本来就是一拨人，手艺和手艺之间没有墙。墙是后来工业分工一块一块砌起来的。而 AI 正在做的事情里，有一件就是把这些墙拆掉，让一个美术生重新可以既画画又造机器。

当然，拆墙的不是我，是 AI。我只是刚好站在墙倒了的地方，顺手多接了几种活儿而已。

我是个什么样的人

说完履历，聊聊我是个什么样的人。

一句话，低精力，偏佛系。

我不是那种能连轴转的选手。社交久了要一个人待着回血，事情多了要放慢节奏一条一条处理。平时最喜欢的事，就是自己一个人慢慢想，慢慢琢磨，想到哪算哪。

一个人琢磨听起来孤独，其实挺爽的。安静的下午，开着编辑器和一个模型，想到什么试什么，试出来的东西摆成一排看。没人催的时候，想法自己会往外长。当然，交期来的时候我也没飘着，佛系归佛系，交出去的东西我不糊弄。

低精力还有个好处，就是对噪音不敏感。热点天天有，风口轮流转，我蹭不动也不想蹭，我的节奏就是把手头这点东西磨顺。你问我错过了什么风口，肯定错过了不少。但我不想追的东西，追到了也拿不住。

当然佛系不等于躺。我给自己划的红线是交付。单子接了就要对得起，时间尽量提前留，宁可慢一点，不给别人添堵。这也是我理解的佛系，不跟别人较劲，但跟自己的活儿较劲。

这种性格在接单这行听起来像缺点。客户都催，同行都卷，一个佛系的人怎么活得下去。

我非常理解这种担心，因为它也折磨过我。

但后来我发现，琢磨这件事，恰恰是这个时代最被低估的动作。低精力的人不适合拼体力，但特别适合拼琢磨。别人把时间花在跑得更快上，我把时间花在想得更深上。而 AI 时代，想得深的东西，反而比做得快的东西更值钱。

这话不是我发明的，是我用真金白银的单子一点点验证出来的。

顺便交代一下我现在的一天大概长什么样。接单的活儿排在前半段，改 agent 的，写页面的，画图的。后半段留给自己，琢磨新东西，磨这个站，磨组件。一天的产出不多，但每天都在磨。我信这个，慢就是快。这话听着像鸡汤，但你把时间轴拉长到三年看，快的人换了三个方向，慢的人已经把一个方向磨穿了。

我对 AI 的态度

然后说说我对 AI 的态度。

我不会说，也不能说，我的 AI 很强。

人外有人，天外有天。这个领域牛人太多了，我永远只是个琢磨者。我希望的从来不是当谁的老师，而是我对 AI 的这些理解和想法，能帮到大家。帮到一个是一个。这也是我把自己的琢磨整理出来、做成这个站的原因。

但有一点我是坚信的。

AI 很厉害。编程、代码开发、办公批处理这些事，它确实牛逼，这个要认。但在想象力面前，它始终追不上人。

该认的要认。比如批处理，以前跑个数据清洗要写脚本调半天，现在描述一遍就出来。比如样板代码，模型写得又快又规矩。这些活儿我已经全交出去了。

毕加索说过一句话，大意是，电脑没什么用，它们只能给你答案。

我第一次看到这句的时候愣了一下。只能给你答案。答案便宜，问题贵。模型能给你一万个方案，但「哪个是对的」「为什么要这个」「这个细节到底长什么样」，这些问题的答案不在模型里，在人脑子里。

这句话有一百个翻译版本，我更喜欢这个大意。因为答案这个事情，现在的模型是真给得越来越多，越给越便宜。但提出好问题的那根神经，它没有。你对一个细节的执念，对一种「不对劲」的敏感，是模型清单里没有的输入项。

举个大家都有体会的例子。模型可以给你一万个按钮的样式，但你的产品该放几个按钮、放在哪、按下之后用户应该感觉到什么，它说了不算。更玄一点，同样一份规格说明，你脑子里「想要的感觉」是唯一的，模型给的一万个版本里可能一个都不在。把它捞出来的能力，就是想象。

所以我给自己定的方向，从来不是用 AI 换掉自己，是用 AI 把自己从答案里捞出来。技术时间归零之后，省下来的每一分钟，我都想花在想事情上。接单也是这个分工，脏活累活给模型，想象力我来。

正所谓那句话嘛，没有做不到，只有想不到，哈哈哈。

技术把「做不到」的门一扇一扇打开，剩下的就全是「想不想得到」的比拼了。这块我在「我为什么做 Solen Design」那篇里展开讲过，那篇算是第二篇，这里就不重复了。这篇先把「我是谁」交代清楚。

正在跑的项目

最后聊一个我实际在跑的项目吧，Solenio，网址 rhyme3.com，一个 API 中转站。

起因说出来特别朴素。我订阅太多了，自己和朋友手里的 Token 总是用不完，每个月都有一部分额度躺在那里过期。浪费啊。于是就搭了个中转站，把这些剩出来的额度用起来。

起初就是自己和朋友用。

后来有粉丝说他们的订阅也用不完，那就一起加进来。用的人多了，站就慢慢越做越大，大到我自己都有点懵？？？现在用量不小了，我们也收官方 Key 来扛。

坦率的讲，这个东西没什么技术含量，就是用一个开源项目，加了我自己的一些改动。我不打算把它包装得很高深，它就是个实用的工具，解决「额度用不完」这个具体的浪费。

有人可能会说，这种站满大街都是。对，满大街都是，但我这个是从「自己的额度用不完」这个真实的浪费里长出来的，不是为了做站而做站。它让我第一次体会到，一个好东西的起点可以特别小，小到只是不想浪费。后面越滚越大，全是顺着真实需求长出来的。

所以如果你们的订阅额度也总是用不完，或者你们也想搭一个自己的中转站，可以来找我，我可以帮你搭一下。

至于搭站这事儿，前面说了没什么技术，但没什么技术不等于没有坑。账号怎么管，渠道怎么挑，稳定怎么保证，全是琐碎活儿。你要是自己折腾烦了，来找我，我把踩过的跟头打包给你。

站里现在跑着各种模型，大家的额度在里面转起来，一点不浪费。我时不时看看后台用量，涨一点，高兴一点。这种慢慢长大的感觉，跟磨一个组件一模一样。

这句话不是客套。我一个人慢慢琢磨，朋友们帮我出出主意、提提需求，这个东西就能长成更方便的样子。互相帮着磨平一些信息差，这事儿我乐意干。

对了，还有一个项目我也提一嘴，叫 Solia，是个 agent。

这个东西目前就我自己和几个朋友在用，没有公布出来。不是藏着掖着，是我不知道它是不是适配大家的需求。因为当时做 Solia，从头到尾都是奔着让自己更顺手去的，它长成什么样，完全由我的使用习惯说了算。

哪怕到现在，我都一直在优化和更新它。

那为什么还要写出来呢。因为我琢磨过一个问题，东西是先适配自己，还是先适配别人，我的答案是先适配自己。一个连自己都用不顺手的东西，硬推给别人，那才是真的坑。等哪天它磨到我觉得，诶，这个别人应该也用得上，我会让它正式见人。

回到那个问题

好，现在可以回答标题那个问题了。

我是谁。

我是一个美术出身、纯手搓起步、被 AI 拐进开发圈的接单侠。我低精力，佛系，喜欢一个人慢慢琢磨。我坚信 AI 打开的是「做不到」的门，而「想不到」的那扇门，永远要人自己去推。

我叫云。慢慢飘，慢慢磨的那种云。

慢慢飘，慢慢磨，这大概就是我给自己写的人设了。剩下的，交给时间和更新频率。

我为什么做 Solen Design

一个接单的人、一群总在问 UI 的朋友，和一套终于不用再现掏的底座。

2026 年 11 月 16 日

署名：Solen·云

事情是这样的。

隔三差五，就有朋友来问我，UI 到底该怎么设计。

不是问那种特别虚的问题，都挺具体的。一个按钮的按压反馈怎么调才不显得廉价，一个玻璃质感的导航条怎么磨才不糊，一组卡片的间距怎么定才不飘。说实话每一个我都能答，因为这些答案在我脑子里，真的。

但每次答完我都有点恍惚。

因为我发现自己回答的方式永远只有两种，要么去我自己的知识库里翻，翻出以前存的某段笔记或者某张截图，要么就是当场发挥想象，凭手感现编一套。

我的知识库其实也没什么高科技，就是一堆散落在各个应用里的笔记和截图。真要用的时候，能不能搜到，取决于我当初存的时候用了什么措辞。而措辞这种东西，三个月后的我跟三个月前的我，根本对不上。

这两种方式都没错，但它们有一个共同的问题，不可复用。

我掏出来的东西，问的人拿走了，下次另一个人来问同样的问题，我再掏一遍。

我自己接活儿的时候也一样。除了这类提问，我平时接一些 agent 定制和产品开发的项目，也接设计单，业余还喜欢捣鼓 vibe coding，做些没什么用但好玩的小东西。做得多了就经常碰到一个局面，我明明知道我要的那个细节长什么样，就在脑子里，很清楚，但就是迟迟做不出来。

捣鼓这件事在我的生活里占比一直不低，我也没觉得它有什么用，纯粹是那种，看到一个念头在手边变成真的，会爽。但你捣鼓得越多，脑子里散装的东西就越多，多到某个时刻你意识到，它们需要一个地方住，不然就永远处在「我想过，但我找不到了」的状态。

为啥做不出来呢。

因为没有整理。

听着有点抽象哈，我说人话。就是你想做一个东西，脑子里有它的样子，但你没有一套现成的语言去描述它，更没有一套现成的零件去拼它。于是只能每次重新描述一遍，重新想一遍，把同一个细节从脑子里往外掏，掏一次，累一次。

你想想看这笔账。一条整理好的答案，掏的时候是零成本。一条没整理的念头，每次掏都要先花力气把它从记忆里捞出来，再花力气把它翻译成对方能听懂的话。一次两次没什么，十年下来，这笔账大得吓人。而且它最阴的地方在于，你从来不会在任何一本账上看到它，它烧掉的全是你以为不花钱的注意力。

更难受的是，描述这个过程是会失真的。同一件事，你这次描述和下次描述措辞不一样，AI 理解的就不一样，出来的东西就是差一口气。你甚至说不清上次那个到底好在哪。。。这种时候真的会有一声叹息。

AI 时代，这个损耗被放得特别大。

我有时候觉得，AI 时代最贵的不是算力，是描述力。算力按量计费，明码标价。描述力没有人给你计价，但它天天在烧。

因为现在做东西快了嘛，模型几分钟就能给你出一个页面，但前提是你得说清楚你要什么。你说不清，它就猜。你重新描述，它重新猜。一来一回，时间全烧在「重新」这两个字上。

我后来想明白一件事。我一直缺的不是技术，也不是工具，是一套底座。一个把我脑子里那些散装的、每次都要现掏的东西，提前磨好、摆整齐、贴上标签的地方。

所以我做了 Solen Design。

这套东西是什么

它是一套设计系统，纯 CSS 打底。一组收敛的 --sd-* 令牌，颜色、字阶、间距、圆角、阴影全部有固定的阶，再加一层极简的元素样式，零依赖，零构建。组件建在这套令牌上，目前收录了 58 个，交互控件、卡片布局、动效交互、图形图表都有。多数组件提供 React、Vue、Svelte、Solid、Preact 和原生 DOM 六种入口，共享同一套框架无关的引擎，行为和 props 完全一致。你用什么框架，就能用什么姿势把它拿走。

动手之前给自己定了几条规矩。视觉上收着来，大面积低饱和的中性色做底，唯一的强调色只留给焦点和交互，字重收在 400 到 600 之间。技术上也倔，所有样式装在 cascade layer 里，你应用里未分层的 CSS 永远优先于库，不用担心被反超。组件可以整库引入，也可以只取你要的那一个。

说实话决定做这个的时候我犹豫过。市面上设计系统一抓一大把，该有的都有，我凭啥再做一个。

后来想通了。我做这个不是为了跟谁竞争，是为了把我自己的每一次现掏，变成一次性的。

我掏一次，磨成组件，写成规格。以后再有人问，我不用掏了，指一下就行。你不信我都没关系，拿走代码自己看，或者拿走那份提示词，让 AI 从零复刻一遍，出来的东西和展示页是一致的。

提示词是唯一事实来源

每个组件都配了一份完整的复刻提示词，写成一页规格说明。尺寸、颜色、构图、动效的算法、可访问性的要求，全在里头。拿这个库里的帆船目录举例，它的提示词里连船的运动方程都写了，加速度多少，阻尼多少，单帧步长上限多少，半隐式欧拉怎么积分，一页纸里全交代清楚。

它不只是文案，它是组件的唯一事实来源。实现和提示词对不上的时候，先判断哪边是对的，然后改对不上的那一边，没有商量。

为啥这么执念呢。

付费的东西变了

你有没有想过，你买一张设计稿，付的钱到底买的是什么。

是技术时间。

一个设计师学三年软件，练五年对齐和留白，才能把你的想法变成一张能看的图。这份训练的成本摊进每一张稿子。你付钱，买的是他手上那门手艺，是他替你省下的、你自己去学的十年。

而且技术时间在当时是刚性的。对齐要手动，间距要手量，一套配色要试几十遍，切图、适配、命名图层，每一件都在吃时间。你想要一个细节再刁钻一点，报价就得再往上走一点。于是大部分人学会了妥协。不是放弃想象，是想象在报价面前自动降级了。

但现在，模型把技术时间压缩到了几秒钟。

你描述一个页面，它几秒钟给你一个能跑的版本。技术时间趋近于零了。那一张设计稿的价格里，剩下的是什么。

剩下的是你说不清楚的那部分。

是审美，是想象。是你脑子里那个「不是这个，但我也说不出要什么」的东西。以前这部分是白送的，藏在技术时间里一起打包卖了。现在，它变成了全部。

这个事儿，历史其实演过一遍。

1839 年，达盖尔摄影法在法国公布。画家保罗·德拉罗什看到之后说了句话，大意是从今天起，绘画死了。

他这么说不是没有道理。绘画最值钱的部分，画得像，被一台机器几分钟干完了。按这个逻辑，画家这个职业应该就地解散。

结果呢。

绘画不但没死，反而在这之后迎来了一波最猛的爆发。印象派出来了。画家们不卷画得像了，卷光，卷色彩，卷情绪。莫奈对着鲁昂大教堂画了三十多遍，画的根本不是教堂，是清晨的光和黄昏的光的区别。

机器接走了技术时间，绘画才第一次变成一门完全付费给想象的手艺。

这个转型也不是一夜之间发生的。印象派刚冒头的时候，作品被官方沙龙拒收，拒得干干净净，后来才有了落选者沙龙，才有了那群自己搭台子办展的人。新技术逼着整个行业换计费方式的那几年，一定是最难受的几年，也一定是机会最多的几年。

你想想看，现在像不像。

只有 Claude 能做吗

众所周知，Claude 的审美强，好多人拿它出设计，效果确实能打。于是就有一种论调，做 AI 设计就得用 Claude。

我不这么觉得。

我不是说 Claude 不强，它确实强。但「只有 Claude 能做」这个判断，我不认。难道哪天封号了，就不做了？这逻辑不通吧。

GPT 也好，GLM 也好，DeepSeek 也好，我都拿来干过活。只要你的输入不是许愿式的，不是「给我一个好看的页面」这种把全部想象力外包给模型的许愿，而是把要什么、不要什么、精确到像素和运动方程地说清楚，模型之间的差异，说实话，没有想象中那么大。

还有一个特别朴素的验证办法。同一份组件规格，你分别喂给几个模型，让它们从零写一遍。出来的东西当然有差异，但差异的形状很有意思，差的从来不是「能不能做出来」，是线条呼吸感的细微不同。规格把下限钉死了，模型决定中限，你的审美决定上限。下限早就够用了，中限都差不多，能拉开差距的，只有上限。

而且你想，组件的代码都直接给你了，六个框架的都有，你甚至可以一行不写直接复制。提示词只是第二扇门，给那些想从零复刻、想改着玩的人准备的。

门都打开了，走进去之后，比的是什么。

是你自己的审美差距，是你自己的想象。

这是个好消息

因为审美和想象这东西，模型抢不走，反而被它放大了。以前你想做一个细节，光是把技术追平就要花掉全部力气，根本轮不到想象上场。现在技术时间归零，你的想象第一次有机会被完整地执行出来。

Solen Design 就是给这个准备的底座。

你不用从令牌开始搭，不用纠结间距取 14 还是 16，不用每次跟 AI 重新解释一遍什么叫克制的冷调。这些我都替你磨好了。你剩下的时间，全部拿去想。

我甚至觉得，以后人和人做出来的东西，差距会比现在大得多，而不是小得多。技术时间抹平之后，大家终于站在同一条起跑线上比想象了。听着有点残酷，以前你还可以说一句「我技术没他好」，现在这句话失效了。但它同时也把门打开了，想象这件事没有学历门槛，没有资历门槛，它只看你平时有没有在养它。

这条小帆船

对了，你现在如果是在网页上看这篇东西，往右边瞄一眼，应该有一条小帆船悬在一条虚线航线上，你读到哪一节，它就开到哪一节。

那也是这个库里的组件。

我为什么要专门提它呢。因为它是我这套逻辑最好的例子。这个东西以前在我脑子里，就是一个「想要一个跟着阅读位置走的目录」的散装念头，每次做长文页面都得重新想一遍船怎么动、航线怎么弯、停下来的时候怎么晃。现在它被磨成了一个组件，六种框架的代码，一份精确到弹簧系数的提示词，谁都能直接拿走。

而且这个过程是复利的。每磨完一个组件，底座就厚一点，下一次现掏的成本就低一点。磨到某一天你会发现，脑子里新的念头冒出来的时候，手边已经有一半的零件了。

从「我脑子里有个念头」到「你能直接用上」，中间隔着的那段路，就是我想用 Solen Design 磨平的东西。

接下来

至于接下来往哪走，我目前在想的是，把它做成一个 agent，或者别的什么形式。坦率的讲还在研究，还没想明白它最终会长什么样。

因为这件事我做不了它的终极形态。我没办法把它做成对任何一个人都合适。你是个后台开发，你要的是快。你是刚上路的设计师，你要的是看懂为什么这么排。你是老手，你只要零件，别挡路。同一套东西塞给这三种人，总有一个人觉得别扭。

但我想尽量做到的是，让每个人用起来方便一点，更好一点。能直接拿走的就直接拿走，想改的能看懂往哪改，不想学的，复制提示词就能跑。

所以如果你也在捣鼓这些东西，欢迎关注一下它的进展，或者更狠一点，直接给我提建议。哪里别扭，哪里缺，你说了，我就磨。这套底座本来就不该是我一个人的闭门造车，大家一起磨，它才磨得动。

当然，这套东西最后能帮到多少人，我心里也没底，可能有些想法还不成熟，我自己也还在一边维护一边改。但方向我是信的。

所以回到开头，UI 到底该怎么设计。

我的答案越来越简单了。别从零开始想，站到一个磨好的底座上想。技术时间已经被机器接走了，别再花钱把它买回来。

剩下的部分，交给想象。

那才是现在真正付费的东西。

MCP

让 AI 编程助手直接查这套目录：搜风格、取设计文档、取组件源码，都在对话里完成，不用你自己翻网页复制粘贴。

MCP 是什么

做页面的时候你大概遇到过这样的流程：在这站上看中一套风格，点开设计文档，全文复制，贴给 AI，让它照着写。组件也一样：翻到组件页、复制提示词、再贴一遍。每用一次，都要人跑一趟。

MCP（Model Context Protocol）是各家 AI 客户端都认的通用接口：你把一个「工具箱」登记给它，AI 就能自己调里面的工具。这套目录自带的 MCP 服务就是一个工具箱——接上之后，你直接说「找一套适合儿童产品的风格，照着做个落地页」，搜目录、取文档这些事，agent 自己就办了。

这一切都发生在你自己的电脑上：服务就是仓库里的一个本地脚本，读的也是本地文件，没有任何数据上传。

怎么接

赶时间的话，在你的项目里跑一行命令就装上了（需要 Node 18 以上；npm 上的包要已发布）：

claude mcp add solen-design -- npx -y -p solen-design solen-design-mcp

Codex 把开头的 claude 换成 codex，写法相同；CodeBuddy 用它的 mcp add-json 子命令，写法见仓库里的 mcp/README.md。配置完重启客户端生效。

想读仓库里最新的一套，就 clone 下来，主流客户端的配置文件都自带了，打开即用：

  • Claude Code、WorkBuddy（CodeBuddy）：读项目根的 .mcp.json，仓库里已带好。
  • Codex：读 .codex/config.toml，仓库里已带好；第一次打开会问你是否信任本项目，信任即可。
  • VS Code（Copilot）：读项目根的 .vscode/mcp.json，仓库里已带好（顶层键是 servers，与别家不同）。
  • Gemini CLI：读项目根的 .gemini/settings.json，仓库里已带好，格式与 Claude Code 相同。
  • Cursor：把下面这段填进它的 .cursor/mcp.json，格式相同。
  • ZCode：Settings → MCP 里加一条，路径写完整路径——仓库放在哪就写到哪，例如 <你的仓库路径>/mcp/server.mjs（ZCode 不解析 ~ 和 ${...} 这类缩写，只认写死的路径）。
{
  "mcpServers": {
    "solen-design": {
      "type": "stdio",
      "command": "node",
      "args": ["mcp/server.mjs"]
    }
  }
}

这套服务零依赖，配置完重启客户端就生效。手动接的话，服务入口就是上面那个文件，装成 npm 包时路径换成 node_modules/solen-design/mcp/server.mjs；其他客户端的写法见仓库里的 mcp/README.md。没接 MCP 的 agent 也有办法：仓库自带两个技能包，.agents/skills/solen-design/ 教它查这套目录，.agents/skills/solen-design-craft/ 教它怎么设计，拷进项目的同名目录即可，详见Skill那一页。

试一试

接好后对 agent 说一句话试试：

用 Solen Design 找一套适合儿童产品的风格，
把它的设计文档给我，再照着做一个落地页。

如果它真的开始自己搜风格、取文档，就说明接通了。要是它说找不到工具，通常是两件事：客户端没重启，或者没在仓库根目录启动——配置里的相对路径是按启动目录解析的。

有哪些工具

一共九个。多数时候你不用记名字，直接说需求就行。五个是查目录用的只读工具：

  • list_categories：看看有哪些分类，每个分类下有多少套风格。
  • search_styles：按关键词搜风格，中英文名、简介、标签都能搜。
  • get_style_doc：取一套风格的设计文档（也就是交给 AI 的复刻提示词），中英双语。
  • search_components：按关键词搜组件。
  • get_component：取一个组件的复刻提示词、参数表和源码。

另外四个是改目录的写工具，要对着完整的仓库用（它们改的就是仓库文件）：

  • audit_catalog：全库体检，查设计文档、详情页、索引行有没有缺。
  • add_style：往目录里加一套新风格。
  • set_style_categories：改一套风格的分类。
  • release：发版，写更新日志。

常见问题

  • 提示项目不受信任：项目级配置只在信任过的项目里生效，在客户端的信任提示里选允许就好。
  • 连不上、看不到这些工具：确认客户端重启过，并且是在仓库根目录启动的。
  • 写工具用不了：装成 npm 包时只有五个读取工具；四个写工具改的是仓库文件，要对着完整仓库用。

Skill

两个技能包：一个教 agent 查这套目录，一个教 agent 怎么设计。前者回答「有什么」，后者回答「怎么做」。

两个包各管什么

  • solen-design：查目录。搜风格、取设计文档、找组件源码、翻参数表——你问「有没有现成的」，它负责找。
  • solen-design-craft：怎么设计。定视觉气质与布局结构、把设计写成规格、落到令牌与动效——你问「这个怎么做才对」，它负责教。

两个互补：查目录解决「有没有」，教方法解决「自己也能写出一套」。后者是从这套库里 151 套风格、464 个组件的做法里提炼出来的，不是泛泛的设计鸡汤——它给的是具体骨架、具体数值、具体检查表。

怎么装

没接 MCP 也能用：把技能包拷进项目的 .agents/skills/ 目录，agent 会自动发现（装完重启一次客户端）。

.agents/skills/
├── solen-design/          查目录
└── solen-design-craft/     怎么设计

仓库里就有这两个目录，拷过去即可；装成 npm 包时在 node_modules/solen-design/.agents/skills/ 里，路径换成那个就行。

怎么设计包里有什么

  • 把视觉风格和布局模式分开：前者是材料、光、色、字，后者是信息怎么排、怎么滚、怎么分栏。两者正交，先定视觉再定布局。
  • 设计前先答五个问题：材料与光、一句话气质、主次、密度、禁止项。答不上来就别动手。
  • 风格文档的 12 段骨架：Colors、Typography、Spacing & Layout、Components、Do's and Don'ts、Surfaces、Elevation、Imagery、Layout，加一段给 AI 用的实现契约与色值速查。每段写什么、常见错在哪。
  • 组件规格要交代的六件事：布局与材质、数据、操作和动效、Props、交付要求、使用示例；以及数值写死、状态要全、给主题留口、动效写参数这几条规矩。
  • 十条横切纪律：从 151 套风格的 906 条 Don't 里归纳出来的——一个光源、一个字体家族、字重成体系、圆角走固定档位、阴影克制、渐变当锚点、不用纯黑纯白、动效有下限、禁项要可验。
  • 落到代码时的硬约定：令牌的名字与值、light-dark() 与 data-theme、三层叠层、组件样式的两种形态、可达性要求。
  • 交付前的 11 条自检清单：可以逐条打勾那种。

试一试

直接对它说需求就行，不用点名技能：

用 Solen Design 的方法设计一个支付确认页：
先定视觉气质和布局模式，再写出风格文档和组件规格，
最后按规格实现。

它会先分清你要的是哪一层——「安静一点的」「像终端那种」是视觉，「一个长页面滚动讲清楚」是布局——然后照着骨架把规格写出来，而不是直接吐一版代码让你返工。

和 MCP 什么关系

MCP 给 agent 的是工具：能真的把这套目录翻出来取给你。技能包给 agent 的是方法：知道拿到东西之后该怎么判断、怎么写。两个都装最好——MCP 负责取，Skill 负责判断。
